Pipeline de Gravação de Datasets — init_lerobot_record_v2.py

Pergunta: a estrutura está boa pra gravar datasets? Dá pra gravar vários rápido e assíncrono — clicar salvar e continuar gravando o próximo enquanto o anterior é encodado? O que dá pra adicionar das fontes oficiais sem refatorar tudo?

Achados de 5 leitores de código (record_v2 + LeRobot oficial) + 2 avaliadores (opções oficiais + crítico adversarial). Toda afirmação tem prova arquivo:linha.

A estrutura está boa pra gravar datasets?
SIM ✓
Com 1 ressalva. PNGs já são assíncronos; o save de episódio é assíncrono na unha (INJEÇÃO 7); parquet frame-exato. Precisa de 1 ajuste localizado pra ficar segura em rajada.
Gravar vários rápido e assíncrono?
PARCIAL ⚠
Vários episódios back-to-back: sim. Mas os saves são serializados — salvar em rajada antes do encode anterior (~13s) trava o controle.
Continuar gravando enquanto o anterior encoda?
SIM ✓*
Para 1 encode em voo: sim, livre. O que não dá é encadear 2 encodes — fechar o próximo antes do atual terminar bloqueia.

TL;DR. O save JÁ é assíncrono: ao apertar A, o thread principal só faz o drain de PNGs (~100ms) + snapshot + cria o buffer N+1, e despacha o trabalho pesado (stats + parquet + encode h264 ~13s) numa thread de fundo. Por isso você grava o episódio N+1 enquanto o N encoda. O único bloqueio perigoso é o _join_save_thread() no início de cada save: se você salvar o N+1 antes do encode do N terminar, o loop de controle trava esperando — e se passar de 2s, o watchdog solta o braço. Conserto principal sem refatorar: trocar o join bloqueante por uma fila de saves.

2 · Respostas diretas

Dá pra gravar o próximo episódio enquanto o anterior encoda? SIM — para 1 encode em voo. O buffer já foi trocado por um novo (N+1) antes da thread iniciar (init_lerobot_record_v2.py:589), e a thread usa o snapshot independente via episode_data= (:610), nunca mais tocando self.episode_buffer. add_frame do N+1 escreve só no buffer novo.
O que NÃO dá: encadear dois encodes em paralelo. Fechar o episódio N+1 antes do encode do N terminar bloqueia no _join_save_thread() (init_lerobot_record_v2.py:564). Em episódios curtos (~1-2s) salvos em rajada, o 2º/3º save fica parado no join; se passar de STALE_S=2.0s, o watchdog do run_g1_server solta o braço (kp→0 em 1.5s). É o único ponto que importa muito no robô real.

Vários datasets distintos numa só sessão? Não — o root é timestamped e fixado na inicialização (init_lerobot_record_v2.py:961-965). Cada dataset novo exige reiniciar o processo. Vários episódios no mesmo dataset: sim, back-to-back (reset_time_s=0, corte manual A/B), teto de 50 eps/sessão.

3 · O que adicionar — fontes oficiais, sem refatorar tudo

prioridade altaesforço: pequeno-localizado

① PRINCIPAL — trocar o _join_save_thread bloqueante por uma FILA de saves

Hoje o save do N+1 bloqueia o thread principal até o encode do N acabar (~13s). Substituir por: uma thread-worker persistente + queue.Queue de snapshots. O patched_save_episode passa a só fazer drain + snapshot + criar buffer N+1 e enfileirar — retornando na hora, sem esperar o encode anterior. A worker consome a fila em série (preservando a ordem que meta.save_episode exige), mas o controle nunca mais trava nos 13s.

embasamento: o próprio core já assume saves em série mutando meta (lerobot_dataset.py:1278 "meta.save_episode need to be executed after encoding the videos"). Alinhado ao streaming_video_encoding oficial ("save_episode near-instant, removes the blocking wait between episodes"): huggingface.co/docs/lerobot/streaming_video_encoding

Cuidados: limitar maxsize da fila (backpressure só no caso extremo); tornar _active_save_episode_index uma estrutura por-save (hoje assume 1 save ativo, usado no discard B em :505-506); o atexit deve drenar a fila inteira.

prioridade médiaesforço: trivial — 1 knob

② Atacar os ~13s de encode: vcodec por hardware (NVENC / 'auto')

O gargalo real do save não é o image_writer — é o encode CPU-bound (~13s/save com libx264). O vcodec já é knob no yaml (yaml:17). A doc oficial do streaming menciona vcodec='auto' que detecta o melhor HW encoder. Cortaria os 13s pra frações disso, encurtando a janela de serialização e descarregando a CPU que disputa com o IK.

embasamento: vcodec é knob oficial (lerobot_record.py:179, VALID_VIDEO_CODECS em lerobot_dataset.py:81). O core nota que o encode já é multithreaded (lerobot_dataset.py:1588-1589) — o ganho vem de mudar o codec/HW.

⚠ Caveat forte: validar que o pyav/ffmpeg do ambiente tem o encoder HW e que o vídeo sai frame-exato/alinhado ao parquet (o treino exige isso).

prioridade médiaesforço: trivial — 1 knob

③ Mais threads/processos no image_writer (acelera o drain)

Passar --dataset.num_image_writer_threads_per_camera=6 (ou 8), ou --dataset.num_image_writer_processes=1 (migra a escrita de PNG pra subprocessos, tirando do GIL do controle). Acelera os ~100ms de drain do thread principal. Não acelera o encode (gargalo real). Ganho marginal e grátis.

embasamento (docstring oficial, verbatim): "We advise to use 4 threads per camera with 0 processes. If the fps is not stable, try to increase or lower the number of threads. If it is still not stable, try to use 1 subprocess, or more." — image_writer.py:139-141
prioridade médiaesforço: trivial — 1 knob

④ Baixar o compress_level do depth de 6 → ~1

O drain no thread principal carrega PNGs de profundidade uint16 16-bit salvos com compress_level=6 (muito mais caro que o RGB nível 1). Em episódio longo a fila pode ter centenas de frames e o drain O(queue_size) pode passar dos 100ms e se aproximar de STALE_S=2.0s. Baixar o nível acelera escrita e drain.

prova: lerobot_dataset.py:1165 (compress_level = 1 if dtype==video else 6) · parâmetro de save_image em image_writer.py:173
atençãonão usar

✗ batch_encoding_size>1 — NÃO consertável de forma confiável hoje

O knob existe e em tese adiaria o encode, MAS nesta versão o vídeo em lote sai invertido e truncado (comprovado no run 20260605_173343: batch=50 → file-000.mp4 reverso com 2090/16453 frames). Os patches INJEÇÃO 3.3/3.4 só evitam o crash (KeyError, correlato à issue oficial huggingface/lerobot#2404), não a corrupção. Além disso, mesmo funcionando, o encode em lote rodaria síncrono no episódio-gatilho (N×13s de pico), sem sobrepor com a captura.

prova: knob oficial (lerobot_dataset.py:680-681); bug do crash é issue oficial #2404 (v0.4.0, PR #2462); a corrupção reverso/truncado NÃO tem fix oficial conhecido. Manter video_encoding_batch_size: 1 (yaml:26).
prioridade baixaesforço: pequeno

⑤ Forçar encode em ProcessPoolExecutor mesmo com 1 câmera

Com 1 câmera de vídeo, o encode cai no ramo sem ProcessPoolExecutor (roda na thread daemon, in-process). Forçar o caminho parallel_encoding tiraria os loops Python por-frame do processo de controle. Ganho pequeno (ffmpeg já não segura o GIL no trabalho pesado) + overhead de spawn por save. A fila de saves (①) e o vcodec HW (②) resolvem melhor.

prova: ProcessPoolExecutor por câmera já existe no ramo parallel_encoding (lerobot_dataset.py:1242-1245). Core: "video encoding with ffmpeg is already using multithreading" (lerobot_dataset.py:1588-1589).
