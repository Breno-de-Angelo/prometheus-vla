Teleoperação G1 — Fluxo de Controle & o Gargalo dos "Degraus"

Pergunta: a teleop estava fluindo bem; onde está o gargalo do controle, e se o Unitree faz 250 Hz, por que dizem que limita a 30 Hz?

Comando em análise:

python init_lerobot_record_v2.py \ --config_path config/record/record_televuer.yaml \ --quest-ip 192.168.68.61 --quest-adb-ip=192.168.68.51 \ --left-arm-limp

Tudo abaixo tem prova arquivo:linha + citação verbatim. O que é hipótese está marcado como tal. Achados de 10 leitores de código (local + fontes originais Unitree/LeRobot) + 2 verificadores adversariais.

TL;DR — o "30Hz" não é regressão, e o gargalo não é onde parecia.

① O loop de IK/teleop roda a 30 Hz nos DOIS (nosso e Unitree original). Os "250 Hz" do Unitree nunca foram IK a 250 Hz — são só uma thread dedicada que re-publica o último alvo ~8× entre updates do IK.
② A suavidade do Unitree vem dessa thread clipar contra a posição MEDIDA (que evolui a cada ciclo → sub-passos reais). A nossa thread existe e roda a 250Hz, mas clipa contra o COMANDO anterior → em movimento suave ela só repete o degrau de 30Hz 250×/s. Esse é o gargalo crítico.
③ O conserto é no _arm_streamer_worker do host — não no robô, não na rede.

3 · Os gargalos (ranqueados, com prova)

crítico provado no código

① Clip do arm-streamer é contra o COMANDO anterior, não contra a posição MEDIDA

Esta é a causa dominante dos degraus — independe de GIL ou rede. Para um movimento suave (delta entre alvos de 30Hz < vmax = 0,08 rad), scale = max(|delta|/vmax, 1.0) = 1.0, então no 1º ciclo de 250Hz: newq = prev_cmd + delta = tgt (salta o alvo inteiro). Nos ~7 ciclos seguintes delta = tgt − prev_cmd = 0 → republica exatamente o mesmo q. Resultado: um degrau de 30Hz repetido 250×/s, sem interpolação.

O Unitree clipa contra a medida (current_q = get_current_dual_arm_q()), que evolui a cada ciclo → cada sub-passo interpola medido→alvo de verdade = suavidade real de 250Hz.

nosso: unitree_g1.py:553 prev_cmd = np.array([self.msg.motor_cmd[mv].q for mv in mvs]) :554 delta = tgt - prev_cmd :563 newq = prev_cmd + delta/scale (vmax=0.08 com vlim=20, dt=1/250) unitree: robot_arm.py:153 current_q = self.get_current_dual_arm_q() # DDS medido :156 cliped = current_q + delta/max(motion_scale, 1.0)

⚠ A docstring do host (unitree_g1.py:528) afirma falsamente que clipa contra a medida "réplica do G1_29_ArmController" — o código faz o oposto. O comentário nas linhas 548-552 admite que trocaram de propósito (clip-vs-medida criava assimetria gravitacional), mas a troca custou a suavidade.

Conserto (2 opções comprovadas no próprio repo):
(a) clipar contra a medida (self._lowstate, que o streamer já lê em :545) como o Unitree — restaura os sub-passos, mas reintroduz a assimetria gravitacional (mitigável com tauff/gravity-comp).
(b) interpolação temporal explícita prev_cmd→tgt ao longo dos 33ms (linear por ciclo) — exatamente o que o G1_RAMP_MODE=interp já faz no bridge (run_g1_server.py:430-435). Não depende da medida e evita a assimetria. É a opção mais limpa, e mantém a rampa no host (sua preferência).
crítico provado no código

② IK gera 1 alvo cru a 30Hz e send_action o escreve sem suavização downstream

O alvo de junta é recomputado só 30×/s e escrito direto em body_joints sem clip nem interpolação. Entre dois solves, o alvo é um degrau constante. Como tanto send_action quanto a gravação no dataset usam o mesmo alvo de 30Hz, o staircase nasce aqui e é gravado no parquet (alvo pré-filtro). Toda a suavidade de 250Hz teria que vir do downstream — que está quebrado por ①.

prova: xr_g1_arm.py:415 sol_q, _ = self.arm_ik.solve_ik(...) xr_g1_arm.py:419-434 body_joints[...] = sol_q[0..13] (nenhum clip/ramp) lerobot_record.py:382 _sent_action = robot.send_action(...) 1×/tick @30Hz
Conserto: não mexer no IK (30Hz está OK e é a mesma taxa do Unitree). A suavidade tem que ser reintroduzida downstream — é o mesmo conserto de ①: fazer os ~8 ciclos de 250Hz produzirem sub-passos reais entre alvos de IK.
moderado provado no código

③ O loop trava em 30Hz pela câmera ZMQ (async_read bloqueante), não pelo precise_sleep

O async_read() (cujo nome sugere "non-blocking") faz new_frame_event.wait()+clear(); como o evento é limpo a cada leitura, a próxima chamada bloqueia até a thread receber o próximo frame da D435 (30 FPS fixos). Logo o teto de 30Hz é I/O da câmera, não CPU: o corpo do loop cabe em 23,3ms (~43Hz) e runs sem gate de câmera chegaram a >300Hz. Quando a câmera cai (medido ~9Hz num run), os degraus ficam maiores.

prova: camera_zmq.py:216-221 if not new_frame_event.wait(...): ... new_frame_event.clear() full_realsenser_server.py:19 FPS = 30 :62 pipeline.wait_for_frames(timeout_ms=1000) run real ep25: n=1360 min=23.32ms mean=33.49ms (29.91Hz)
Conserto: desacoplar comando da câmera — já existe a thread de 250Hz; basta ela produzir sub-passos reais (conserto ①). Subir o fps do record só ajuda se a câmera também publicar ≥ esse valor.
moderado hipótese — precisa medição

④ GIL: a thread de 250Hz (Python puro) competindo com câmera + dataset + CRC no mesmo processo

O _arm_streamer_worker é uma thread Python no mesmo GIL que: 2× decode de câmera (json+base64 antes do cv2 que libera GIL), o framing do dataset, e o próprio CRC pack (245 leituras + struct.pack por ciclo, dentro do lock). O IK (CasADi/IPOPT) e numpy liberam o GIL no C++, então não são os maiores seguradores. Ressalva: o Unitree tem a mesma topologia (thread 250Hz + IK 30Hz no mesmo processo) e é suave — a diferença é que ele isola a mão em Process separado, enquanto nós acumulamos mais threads Python no mesmo processo. Efeito real na taxa precisa medição.

Como confirmar: instrumentar time.perf_counter entre ciclos do streamer no robô real. Se confirmar jitter <250Hz, mover o CRC pack pra fora do lock e/ou isolar as câmeras em processo. Secundário — mesmo a 250Hz perfeitos o staircase persiste por ①.
menor provado no código

⑤ CRC pack pure-Python dentro do _arm_lock a 250Hz

Nosso _arm_lock segura o ciclo inteiro (CRC pack de 245 leituras + Write) dentro do lock; o Unitree segura o lock só pra copiar 2 variáveis e faz CRC+Write fora. Aumenta o lock-hold e atrasa o send_action, mas não starva o streamer. Higiene.

prova: unitree_g1.py:541-576 (CRC+Write dentro do lock) vs robot_arm.py:166-181 (lock só copia; CRC/Write fora)
desmentido provado no código

✗ run_g1_server NÃO é o gargalo (em RAMP_ONBOARD=0 é forward transparente)

No default RAMP_ONBOARD=0, o cmd_forward_loop só repassa ZMQ→DDS sem reprocessar — não suaviza nem piora; apenas propaga o degrau que já vem do host. O conserto certo é no arm-streamer do host, não na ponte.

prova: run_g1_server.py:88 default '0' · :455 cmd_forward_loop recv() → DDS Write (sem reprocessamento)

5 · Respostas diretas

Por que 30Hz, se o Unitree faz 250Hz?
Porque o IK/teleop dos dois roda a 30Hz. No Unitree é o --frequency default=30.0 (teleop_hand_and_arm.py:76,477); no nosso é o fps=30 do record, reforçado pelo async_read bloqueante da câmera (30 FPS fixos). Os "250Hz" do Unitree são exclusivamente a thread dedicada _ctrl_motor_state que re-publica o último alvo ~8× entre updates do IK. IK = 30Hz nos dois250Hz = só republish
O Unitree realmente faz 250Hz? Então onde está a diferença?
Sim, mas 250Hz de publish, não de IK. A suavidade real vem da thread re-ler a posição medida a cada ciclo e clipar medido→alvo com passo máx 0,08 rad — como a medida evolui, cada sub-passo interpola de verdade. Nós temos a thread de 250Hz, mas ela clipa contra o comando anterior: em movimento suave salta o alvo no 1º ciclo e repete nos 7 seguintes → só repete o degrau de 30Hz. unitree: clip vs MEDIDO ✓nosso: clip vs COMANDO ✗
Onde está o gargalo, afinal?
Em dois pontos do host (não no transporte, não no robô): (1) o _arm_streamer_worker clipa contra prev_cmd em vez do medido → zero interpolação; (2) o IK escreve o alvo cru a 30Hz e o downstream (que deveria suavizar) está quebrado por (1). Não é o run_g1_server (forward transparente) nem a mão (já interpola). GIL é hipótese secundária — mesmo a 250Hz perfeitos, o staircase persiste por (1).
O que medir no robô real para fechar a conta?
① Instrumentar a taxa real de publish do _arm_streamer_worker (logar perf_counter entre ciclos) — fecha a hipótese de GIL.
② Logar prev_cmd, tgt, newq por ciclo num movimento suave — confirma que delta zera após o 1º ciclo.
③ Comparar q comandado × q medido no tempo — vê os platôs de 33ms.
④ Medir o dt real do record (há um IgnoreFPSWarningFilter escondendo o aviso "Record loop is running slower" em init_lerobot_record_v2.py:853).
